Field Desk scraping — the full grug guide

grug small brain but grug explain EVERYTHING now: every stage, what code do, why it there, and where machine get tired. file:line on every claim.

Field Desk is a robot that watches the public Meta Ad Library all day and night, hunting two things: emerging mobile apps (small apps that just started buying ads, before they get big) and web-to-app funnels (the quiz/landing pages advertisers run before the app store). It scrapes ads, decides which advertisers are worth keeping, fetches their real detail, scores them, and shows a ranked feed to a human who thumbs them up or down. This doc walks the whole machine, top to bottom.

00 the whole machine in one breath

Before the detail, here is the river every piece of data flows down:

keyword → scrape Meta → raw ads → classify & dedupe → discovery.candidates (cheap rows) → triage (look up in app store, drop the big/established ones) → promote survivors to public.advertisers + public.apps → enrich (fetch ad history, creatives, funnels, reviews) → weekly snapshots build a growth series → GemScore ranks everyone within their cohort → frontend.emerging_scaling_apps matview → the feed → human 👍/👎 → preference model learns what the human likes.

Two things feed the front of that river: the static taxonomy (a hand-written list of ~305 keywords) and the keyword flywheel (which is supposed to grow new keywords automatically from the gems already found). The flywheel is the engine of novelty — and it's the part that has stalled, which is the whole reason this doc exists.

grug build river so water flow one way. cheap stuff first (just a page_id and a like-count), expensive stuff (fetch the whole app, render the funnel) only for the few that survive triage. grug never spend the costly proxy gigabyte on app grug already know is too big. funnel get its own parallel river beside the app river — same water, different fish.

run_once() is the heart. It runs thirteen stages in order. Each stage is wrapped so a failure in a late stage (funnel, repair) can't kill the early stages that matter most. Here is what each one actually does:

Between the heavy stages the worker touches a heartbeat file (§12) so a healthcheck can tell a hung worker from a merely-slow one.

02 the scrape — one GraphQL call to Meta

Meta has no official API for this. The Ad Library website itself talks to a private GraphQL endpoint, so Field Desk impersonates the website: it holds the same cookies and CSRF tokens a browser would, and POSTs the same query. One function, search_ads(), does it.

src/agf/extract/search.py:9, 48 · request.py:7–57

POST https://www.facebook.com/api/graphql/

form body:
  variables = { queryString, countries, activeStatus, searchType, sortData, cursor }
  doc_id    = 24922295957467452     # the "which query" id — see §03, it's healed live
  lsd, jazoest                      # anti-CSRF tokens scraped from a warmed page

The keyword you're searching becomes queryString. The taxonomy layer the keyword belongs to decides how strictly Meta matches it — this is the difference between finding a precise funnel phrase and casting a wide net:

03 sessions, warming & doc_id healing

A raw HTTP request to that endpoint gets rejected — Meta wants a "warmed" browser-like session first. The SessionPool handles this with a warm-once, reuse-many policy.

src/agf/extract/session_pool.py · token_heal.py

_warm():
    session = make_session()                  # a TLS client over the proxy
    html    = session.warm_get(warm_url)       # GET the real Ad Library page
    tokens  = heal_from_html(html, session)    # scrape lsd + jazoest + heal doc_id from JS

acquire():  return current session, or _warm() if missing/stale (> 30 min old)
invalidate(): drop the session so the next acquire() re-warms on a FRESH proxy IP

So the flow is: warm a session once (one real page load), reuse it for up to 30 minutes of searches, then re-warm. "Healing the doc_id" means parsing Meta's JavaScript bundles to find the current GraphQL query id, because the hardcoded 24922295957467452 is only a fallback that goes stale when Meta ships new code. invalidate() is the panic button — called whenever a request comes back banned or challenged — and it forces the next request onto a brand-new residential IP.

04 the club — anti-bot handling

Meta fights scrapers two ways, and the code answers each.

rd_challenge — the 403 wall

rd_challenge.py:1–26 · tls_client.py:54–63

Sometimes Meta returns HTTP 403 with a little JavaScript puzzle (a path like /__rd_verify_abc123). The code detects this, POSTs the verify path to mint a pass-cookie, and retries — up to 2 solves before giving up and raising a SESSION error (which triggers a re-warm on a fresh IP). 

if status == 403 or body contains "/__rd_verify_...":
    POST /__rd_verify_abc123?challenge=N      # solve, get pass cookie
    retry (max 2), else raise SESSION error → re-warm

1675004 — the real rate limit

backoff.py:40–78 · search.py:83 · facade.py:60

The sneaky one. When you've asked too fast, Meta does not return HTTP 429. It returns a normal 200 OK with an error buried inside the JSON body. So every single response is run through raise_for_fb_error(), which opens the JSON and checks the error code: 

if parsed.errors[0].code == 1675004:           # the rate-limit code
    delay = min(30s, 0.5s · 2**attempt) + jitter   # exponential backoff, up to 4 tries
    pool.invalidate()                          # throw away this proxy IP, re-warm fresh
grug learn the hard way: the ban is not a slammed door (429). the ban is a smiling 200 with poison inside the box. so grug open EVERY box and sniff. poison found → grug wait longer each time, AND throw away the house grug was standing in (the residential IP) and walk into a new house. datacenter house get clubbed instantly; rotating residential house survive. this why DataImpulse cost real money per gigabyte — grug pay for many houses.

05 discovery sweep → candidates

Now the actual hunt. run_sweep() loops over the taxonomy entries. For each keyword it scrapes a few pages, classifies each ad, drops duplicates within that result set, and upserts survivors into discovery.candidates.

src/agf/discovery/sweep.py:77–109

for entry in entries:                                  # one taxonomy keyword each
    pages = min(entry.max_pages, max_pages)             # per-kw ceiling vs prod cap (AGF_SWEEP_PAGES)
    ads   = extractor.search(query=entry.keyword, countries=["US"],
                             search_type=entry.search_type, max_pages=pages)
    for ad in ads:
        disp, row = classify_candidate(ad, keyword=entry.keyword, technique=entry.layer)
        if disp != "candidate": stats["drops"][disp] += 1; continue
        key = (page_id, store, store_id)                # dedupe WITHIN this serp
        if key in seen: continue
        rows.append(row)
    for row in rows:
        _, was_new = upsert_sweep_candidate(conn, row)
        stats["candidates_new" if was_new else "candidates_seen"] += 1

classify_candidate — the cheap inline filter

sweep.py:40–59

Before a candidate is even stored, four cheap checks run on the ad — no store lookup needed yet:

  • no_link — the ad has no destination URL, useless.
  • social — the link just points back to facebook/instagram, not a real destination.
  • incumbent_likes — page_like_count > 10,000. A page with 10k+ likes is already established, not emerging, so drop it now and never pay to look it up.
  • then classify_url(link_url): if the URL resolves to an iOS or Android store id, it's an app candidate; otherwise it's non_app (which the funnel pipeline handles instead).

the candidate row & the exact upsert

db/candidates.py:12–24 · schema/112_discovery_candidates.sql

A candidate is deliberately thin — just what the ad already told us (page_id, like-count, store id, the keyword that found it). The upsert is keyed on (page_id, store, store_id) so the same app found by ten keywords is one row, not ten: 

INSERT INTO discovery.candidates (page_id, page_name, page_like_count, store, store_id,
       link_url, cta_type, ad_start_date, source_keyword, technique)
VALUES (...)
ON CONFLICT (page_id, store, store_id) DO UPDATE SET
  times_seen      = discovery.candidates.times_seen + 1,
  last_seen_at    = now(),
  page_like_count = COALESCE(EXCLUDED.page_like_count, discovery.candidates.page_like_count)
RETURNING id, (xmax = 0) AS was_new

That last line is the trick behind the new=1 seen=945 log line. In Postgres, xmax = 0 is true only when the row was freshly inserted, not updated. So was_new tells the sweep whether it found something genuinely new or just bumped times_seen on a row it already had.

this the exact spot where the dryness shows. 945 of the things grug found this sweep were UPDATE — apps already in the box, just seen again. 1 was a true INSERT. grug is re-walking the same field and the field is picked clean. the candidate is cheap by design, so grug can throw most away, but cheap-and-already-owned is still wasted proxy money.

06 triage — keep or drop

The sweep stored thin rows. Triage is where each candidate is judged: it's looked up in the real app store (iTunes for iOS, Google Play for Android), and the store facts decide its fate. This is the gate that keeps the database focused on emerging apps.

src/agf/discovery/triage.py:21–94

def triage_decision(meta):
    if meta is None:                          return "dropped", "no_us_listing"   # can't verify it
    if meta.is_game is True:                  return "dropped", "game"            # out of scope
    if (meta.installs or 0)     > 100_000:    return "dropped", "installs_over_threshold"
    if (meta.rating_count or 0) > 5_000:      return "dropped", "ratings_over_threshold"
    return "kept", None

# kept → _promote(): upsert_advertiser() + upsert_app()
#                    writes public.advertisers + public.apps, the "real" tables
# then mark_triaged(status, drop_reason, kept_advertiser_id)
drop reasonrulewhy
no_us_listingstore lookup emptycan't confirm it's a real US app
gameis_gamegames are a different market, excluded
installs_over_thresholdinstalls > 100,000already established — not a hidden gem
ratings_over_thresholdratings > 5,000already established

Two design choices matter here. First, NULL always passes — if the store didn't report installs, the app isn't dropped on a guess; the system would rather keep a maybe than lose a gem. Second, if the store lookup itself fails (a network blip), the candidate stays in new status and is retried next cycle — it isn't punished for the scraper's own bad connection. Survivors are promoted into the real public.advertisers and public.apps tables, which is what everything downstream reads.

06A the App Store side

Everything so far was Meta. But an "app candidate" is only a store link until the system asks the actual App Store / Google Play who it is. That store lookup is used in three places: triage (§06 — installs/ratings decide keep-or-drop), enrich (§10 — full detail), and the growth signal (§09 — daily install/review snapshots). All of it is Apple/Google traffic — zero Meta calls.

src/agf/enrich_full/appstore.py · reviews.py · app_refresh.py · sidecar/

iOS — the iTunes Lookup API

One cheap public endpoint, batched up to 200 ids per call:

GET https://itunes.apple.com/lookup?id=111,222,...&entity=software&country=us

07 the funnel pipeline + the app bridge

Funnels run as a parallel river beside the app sweep, with the same scraping machinery but different keywords (the funnel_phrase layer) and a different destination table. The key function is classify_funnel_candidate, and it has one clever twist — the bridge.

src/agf/discovery/funnel_sweep.py:30–69, 121–128

if intent.kind in ("ios","android"):          # a funnel keyword found a STORE link...
    if not intent.store_id: return "app", None
    return "app", {... technique:"funnel_sweep"}   # *** BRIDGE: route it to the APP river ***
elif funnel_signal(ad, technique):            # a real web landing page with funnel markers
    return "candidate", {...}                  # → discovery.funnel_candidates

Sometimes a funnel keyword like "take the quiz" surfaces an ad that links straight to the app store rather than a web page. Rather than waste it, the bridge re-routes that app-backed candidate into the same discovery.candidates table and the same triage flow — it shows up in the log as bridged=34. Web funnels that aren't app links go to funnel_candidates, where a later confirm stage renders them to verify they're genuine funnels.

Funnels are allowed to be much bigger than apps: the incumbent ceiling is 5,000,000 likes, not 10,000. That's deliberate — a proven funnel operator legitimately runs at huge scale, and we want to study the winners, whereas an emerging app with 5M page likes is by definition no longer emerging.

08 the keyword flywheel — how new words are born

This is the most important section, because this is the part that has stalled. The static taxonomy is finite and hand-written. The flywheel's job is to grow the keyword list automatically, by reading the ad copy of gems it already found and mining out new phrases to search. When it works, the system expands its own reach. Right now it mines zero.

mine_phrases — the mining algorithm

src/agf/discovery/keyword_mining.py:103–151

It takes a corpus of ad bodies and returns the best new candidate phrases. Step by step:

def mine_phrases(corpus, *, exclude, min_advertisers=2, limit=10):
    # corpus = [(advertiser_id, body_text), ...] from fetch_gem_copy(min_score=40)
    # 1. phrases_of(text): break each sentence into 2–4 word n-grams.
    #    word regex [a-z0-9][a-z0-9'-]*. If a sentence has accented chars → reject
    #    (it's not English, skip the whole sentence).
    # 2. _phrase_ok: drop phrases starting/ending on a stopword; REQUIRE at least one
    #    "real" token (len ≥ 4, not a stopword, not a weak filler word).
    # 3. count how many DISTINCT advertisers used each phrase.
    # 4. keep a phrase only if:  min_advertisers ≤ #advertisers ≤ max(5, 10% of corpus)
    #    AND it's carried by a RARE word (used by ≤ max(5, 5% of corpus) advertisers).
    # 5. exclude: bidirectional substring vs (static taxonomy ∪ every tried keyword).
    #    "habit tracker" is dropped if "habit tracker app" already exists, and vice-versa.
    # 6. rank: most advertisers first, then longest phrase, then alphabetical;
    #    drop a shorter phrase if a longer one already covers it.
    # 7. return the top `limit`.

The intuition: a good new keyword is a phrase that several different advertisers independently use (so it's a real category, not one company's slogan) but not too many (or it's a generic cliché), and it must contain at least one distinctive, rare word (so "the best app" is rejected but "wall pilates workout" survives).

the trial budget — promote or retire

src/agf/db/dynamic_keywords.py:25–106

A mined phrase doesn't go live immediately. It enters as a trial keyword and gets a few sweeps to prove itself. The dynamic_keywords table tracks its state: 

columns: keyword, kind('app'|'funnel'), source, status('trial'|'active'|'retired'),
         sweeps_used, new_candidates_total, last_swept_at    UNIQUE(keyword, kind)

TRIAL_SWEEPS    = 4   # AGF_FLYWHEEL_TRIAL_SWEEPS   — 4 sweeps to prove itself
PROMOTE_MIN_NEW = 3   # AGF_FLYWHEEL_PROMOTE_MIN_NEW — must net ≥3 new candidates

apply_verdicts():   # the judgment, run every cycle
  UPDATE dynamic_keywords SET status = CASE
      WHEN new_candidates_total ≥ 3 THEN 'active'   # earned its place, keep sweeping
      ELSE 'retired'                                # a dud, never sweep again
  END WHERE status='trial' AND sweeps_used ≥ 4

run_flywheel_stage — the loop, and the three gates that produce mined=0

src/agf/workers/main.py:339–384

why mined=0 right now — three gates, any one shuts the well:
1. room ≤ 0 — 40 trial slots already full, no space to mint more.
2. empty corpus — fetch_gem_copy only returns ad copy from gems scoring ≥ 40; if few gems clear that, there's almost nothing to read.
3. the real killer: exclude = static ∪ tried, and tried is every keyword ever minted — including retired ones. Plus the substring rule. So any phrase the gem copy contains, grug has already tried, and it's already in the forbidden set. Ad copy is thin and repetitive ("lose weight", "AI powered", "personalized plan") — grug mined that field bare moons ago, and grug never forgets a word it tried. Thin corpus + permanent memory = zero new keywords.
shipped fix (Phase 0): the promotion bar was the silent killer. PROMOTE_MIN_NEW demanded 3 new candidates inside 4 shallow sweeps — unreachable at real yields, so the verdict retired 94% of app trials and 100% of funnel trials. Even when a keyword worked, it got killed. Lowered the default to 1 (commit 22832b3): a keyword that finds even one new app now survives. This doesn't refill the corpus — that's the release-expand stage in §13 — but it stops the renewal engine from strangling itself.

The funnel flywheel (run_funnel_flywheel_stage, corpus = fetch_funnel_copy, max_trials=30, min_advertisers=2) is the identical machine on a separate pool — and it still finds new keywords, because funnel landing-page copy is far richer and more varied than the few words in an app ad. That asymmetry is exactly what the live log shows: funnel side productive, app side dry.

09 building the growth signal

This is the quiet machinery that the snippet-version of this doc skipped, and it's essential: an app's GemScore is mostly about how fast it's growing, and "growth" only exists if the system records a time series. Three stages build that series every cycle.

1.5 — the weekly velocity snapshot

main.py:450–459 · snapshot_advertiser_week()

Every tick, this counts each tracked advertiser's currently-active ads and writes one row into the weekly app_advertiser_metrics series. It adds no Meta traffic (it just counts rows already in public.ads). The code comment is blunt about why it matters: without it, "the week-over-week signal never builds, scaling_velocity stays flat, and no advertiser can EVER cross the alert threshold no matter how long the system runs." It's the metronome the whole score depends on.

1.7 — app-store refresh

main.py:471–491 · app_refresh.py

Once per day per app, this re-pulls the store listing (icon, screenshots, price, install count) and writes a fresh adtech.app_metrics row — the app-side growth series, parallel to the ad-side one. The delta in install count and review count over 28 days is what becomes the Demand axis. It's scoped to apps missing today's snapshot, so even an hourly sweep hits the store APIs at most once per app per day.

1.8 — keeper history

main.py:493–505 · keeper_history.py

Here's a subtle bootstrapping problem. Triage promotes a new app with advertiser + app rows but zero stored ads — so it has no history, so it can't score, so it would be invisible forever. Keeper history fixes this: for each freshly-promoted keeper it does one active_status=ALL pull of the advertiser's whole ad listing and reconstructs the last 16 Monday-aligned weeks of activity. It spends half the discovery enrich budget (enrich §10 keeps the other half).

11 GemScore — the exact formula + vetoes

With history and detail in place, scoring ranks everyone. Crucially, ranking is relative to a cohort (apps grouped by genre): each axis is a 0–1 percentile against the gem's peers, so "fast-growing" means fast compared to similar apps, not in absolute numbers. Then the axes combine:

src/agf/scoring/gemscore.py:66 · run_scoring.py

GemScore = 100 · SV^0.42 · UR^0.12 · FI^0.03 · D^0.38 · W^0.05
           (a missing axis imputes to floor 0.5 — a data gap won't zero the score)

It's multiplicative on purpose — an "AND gate". A gem can't win by spiking one axis; it has to be at least decent across several. The two heavyweights are SV (.42) and D (.38) — durability of its ad winners, and real store-side demand growth.

axisexpbuilt from all percentile-in-cohort
SV scaling velocity.42winner_age .40 (longest-running ad, capped 35d) + winner_depth .30 (# ads running ≥21d) + count_growth .15 (max(0, log-growth) — a shrinking ad count never punishes) + iteration .15 (how fast they launch new ads)
D demand.38installs .55 + reviews .45, each a velocity = delta per day over 28d
UR under-radar.12rating .40 + followers .20 + reach .20 + newness .20, all inverted (1 − pctile): the more known it is, the lower this scores
FI funnel intent.03fingerprint .50 (has a funnel) + cta .30 (install CTA) + monetize .20
W whitespace.05crowding = how many sustained advertisers share the gem's source keyword; 1 − pctile (emptier niche = higher)

12 the feed, repairs & self-healing

the feed matview & the funnel link

db/schema/129_emerging_matview_funnel_ungated.sql:86–100

The feed reads frontend.emerging_scaling_apps, a materialized view gated on alert = TRUE. It joins each gem to app metadata, its growth series, and — via a LATERAL subquery — its most recent real funnel URL. The "real" part is a regex that excludes store and social redirects, so the directory's Quiz link only appears when there's a genuine off-store landing page: 

SELECT coalesce(f.final_url_after_redirect, f.landing_url) AS funnel_url
FROM public.funnels f JOIN public.ads a ON a.id=f.ad_id
WHERE a.advertiser_id = s.advertiser_id
  AND url ~* '^https?://'
  AND url !~* '(apps.apple.com|play.google.com|facebook|instagram|tiktok|youtube|t.me|linktr.ee|...)'
ORDER BY f.captured_at DESC LIMIT 1

the repair stages (3.5, 3.6)

Enrich only deep-fetches the top-N active ads, and apps below the alert threshold never get enriched at all — so some feed apps end up with no downloaded creative or no captured funnel. The two repair stages drain those backlogs a few advertisers per cycle, bounded and isolated so they can never abort the main pipeline. Over many cycles the gaps fill in.

staying alive 24/7

main.py:646–721

This is what makes continuous operation survivable:

  • heartbeat — _touch_heartbeat() writes a timestamp file at each stage boundary.
  • healthcheck — --healthcheck exits non-zero only if the heartbeat is stale beyond 2 × interval + 300s. The budget clears one full ~40-minute cycle, so a worker mid-sweep doesn't read as "down" (that was a real bug once), but a genuinely hung one still trips.
  • run reaping — at startup, reap_open_runs() closes any run-rows orphaned by a crash or SIGTERM. No run survives a restart, so every still-open row is stale; reaping keeps the daily-gate logic honest. That's the reaped orphaned runs line in the log.

The throughline: the bottleneck is not scrape speed, it's novelty. The machine has eaten all the food in this room. Running it harder just re-pays proxy money to re-find apps it already owns, while accumulating stall risk. The only live frontier is new keywords, and the well that makes them (gem ad copy) is bare.

the fix that shipped — a new door: App Store new-releases → Meta typeahead

The flywheel can only ever mine its own ad copy, so it digs the same basin deeper. The cure is an external source of emerging apps. App Store new-releases are perfect: an app on the new-releases list launched this week (userRatingCount=0), spans every store category, and Apple's RSS is free (zero Meta traffic to fetch). That's the new door (stage 1.93, off by default behind AGF_RELEASE_MINT).

But grug tried the obvious thing first and it failed — worth writing down so nobody re-tries it:

triedlive resultverdict
mine keywords from new-release app names0 keywords — names are brand-y ("Fandogh", "Winner 105"), almost nothing recurs across appsdead end
mine keywords from store descriptionsrecurs, but only boilerplate — "terms of use", "privacy policy", "designed to help"dead end
typeahead on the app namethe apps that actually buy Meta ads surface as advertiser pages (page_id + likes)shipped

So instead of minting keywords, the stage feeds each new app's name into Meta typeahead (search_pages_typeahead, doc_id 9755915494515334) and resolves the new advertiser pages to candidates through the exact same path the keyword sweep uses — classify_candidate → upsert_sweep_candidate → triage (§05–06). It's budget-disciplined: it skips pages already in the DB (no re-walking), vetoes incumbents by their typeahead like-count before scraping, and caps how many listings it scrapes per run (AGF_RELEASE_MINT_MAX_LISTINGS). Shipped in commit a76b391, daily-gated by migration 134.

scrape ALL categories, rank narrow. The new door pulls new-releases from every store category — not just the health/self-improvement ones grug has liked before — minus only games (out of product scope) and stickers. Why: a hidden gem is by definition in a category you're not already looking at, so if your 👍/👎 decided what gets scraped, you'd loop forever on the same apps. Preference belongs at the feed (the p_like model picks what surfaces to you); the scrape gate stays blind to taste and only enforces structural limits (emerging-only via the incumbent veto, no games). Look everywhere; show what you'd like.
big idea: don't dig the same hole deeper — open a new door. The flywheel eats its own ad copy, so it can only ever find more of what it already found. The App Store new-releases list is a fresh stream of apps grug has never seen, every single day. grug asks Meta "do any of these buy ads?" via typeahead, and the ones that do walk straight into the pipe. grug tried to squeeze keywords out of their names and descriptions first — names too thin, descriptions all "terms of use" lawyer-speak — so grug skipped the keyword step entirely and grabbed the advertiser pages direct. new door good.
